# Zoom Attendance Telemetry PoC — Технічний опис проєкту

Цей документ підготовлено для подальшого аналізу, архітектурного ресерчу та розширення системи у розмовах з AI-моделями (Gemini) та технічною командою.

---

## 1. Мета та бізнес-контекст проєкту

### Головна ціль:
Автоматизувати та валідувати облік фактично проведених уроків мовної школи через Zoom API. Система призначена для усунення розбіжностей між запланованими заняттями, діями викладачів та фактичною присутністю учнів.

### Бізнес-задачі:
1. **Підтвердження факту проведення уроку (Proof of Delivery):**
   * Чи дійсно відбувся урок?
   * Чи тривав він достатньо часу (наприклад, $\ge 30$ хв)?
2. **Контроль відвідуваності та «No-Show»:**
   * Чи підключилися учні до уроку?
   * Чи чекав викладач учнів самостійно (кейс No-Show зі сторони студента, за який вчителю нараховується компенсація за очікування)?
   * Хто конкретно був присутній (унікальні ідентифікатори, email, час входу/виходу)?
3. **Облік робочого часу для нарахування зарплати викладачам:**
   * Точна агрегація сумарного часу викладачів за обраний розрахунковий період (тиждень, місяць тощо).

## 3. Архітектура та структура проєкту

```text
poc-zoom-report/
├── api/
│   └── report.js          # Vercel Serverless Function (Zoom OAuth, Data Aggregation, Logic)
├── public/
│   └── index.html         # Frontend клієнт (Mobile-first дашборд, прогресивний фетчинг)
├── index.html             # Дзеркальний корінь для альтернативних конфігурацій Vercel
├── test-api.js            # Інтеграційний тест ендпоінта api/report.js
├── .env                   # Локальні кредити Zoom OAuth (не в репозиторії)
├── .env.example           # Зразок необхідних змінних середовища
└── package.json           # Конфігурація проєкту ("type": "module")
```

### Стек технологій:
* **Backend:** Node.js Serverless Function на Vercel (ES Modules).
* **Автентифікація:** Zoom Server-to-Server OAuth.
* **Зовнішній API:** Zoom REST API v2 (`/users`, `/report/users/{id}/meetings`, `/report/meetings/{id}/participants`).
* **Кешування:** In-memory кешування OAuth токена (з урахуванням TTL).

## 4. Специфікація API ендпоінта (`api/report.js`)

### Параметри запиту:
* `from` (YYYY-MM-DD): Початкова дата вибірки (за замовчуванням — поточний день за київським часом `Europe/Kyiv`).
* `to` (YYYY-MM-DD): Кінцева дата вибірки.
* `overview` (`true` | `false`): Режим швидкого опитування метаданих зустрічей без отримання списків учасників.

### Режими роботи:
1. **Overview mode (`overview=true`):**
   * Виконує один легкий запит до Zoom Report API на користувача.
   * Повертає структуру днів, розклад уроків, початкову тривалість і кількість учасників.
   * Час відповіді: **< 900 мс** на весь місяць.
2. **Detailed mode (повний звіт по дню/періоду):**
   * Робить чанковані запити до Zoom Participants Report API для кожного уроку.
   * Агрегує сесії, розпізнає організатора/вчителів, студентів, час входу та виходу.

### Класифікація статусів уроку:
* `VERIFIED` («Верифікований урок»): Тривалість уроку $\ge 30$ хв, учасників $\ge 2$, присутній щонайменше 1 учень.
* `ONLY_HOST` («Тільки викладач (No-Show)»): Тривалість уроку $\ge 15$ хв, учні відсутні (лише викладач у кімнаті).
* `SHORT_CALL` («Короткий дзвінок»): Тривалість $< 15$ хв або технічний вхід.

## 5. Ключові технічні проблеми, виявлені під час дослідження, та їхні рішення

### Проблема 1: Rate Limiting Zoom API (HTTP 429 Too Many Requests)
* **Контекст:** Zoom Report API має строгі ліміти (Tier 2/Resource-based — не більше 3 запитів на секунду).
* **Симптом:** При спробі завантажити місячний звіт (20–30 занять) монолітний бекенд падав з помилкою 429 або зависав на 6+ секунд.
* **Рішення:**
  1. На бекенді впроваджено чанкінг (обробка по 2 зустрічі) з паузами 200 мс та експоненційним Retry-механізмом при отриманні 429 (`Retry-After`).
  2. На фронтенді впроваджено **двоетапний прогресивний флоу**: швидкий `overview` запит повертає каркас розкладу за 0.8 с, після чого клієнт послідовно фетчить дні по одному (`?from=date&to=date`). Це повністю розвантажило ліміти API та запобігло тайм-аутам Vercel (10с limit на безкоштовному тарифі).

### Проблема 2: Ідентифікація викладачів («Спільний обліковий запис» vs «Персональні імена»)
* **Контекст:** Організація використовує єдиний спільний корпоративний Zoom-акаунт (наприклад, `Empire Group`, `darya.loboda@...`). Проте фактичні уроки ведуть різні вчителі (*Heather Puffett*, *Mariana Hasiak*, *Elena Petrenko*), запускаючи Zoom-клієнт зі своїх комп'ютерів.
* **Симптом (Кейс 4 вересня):** 4 вересня відбулися дві зустрічі, де вчителі чекали на учнів (No-Show). Оскільки їхні імена не збігалися з `Empire Group`, а пошта в списку учасників була порожня, старий алгоритм позначав вчителя як «Учня», показуючи дивний стан: «1 гість і 0 викладачів».
* **Рішення:**
  * У Zoom Report Participants API організатор кімнати (Host) завжди має системний ідентифікатор сесії `user_id === '16778240'` (0x01000000).
  * Реалізовано перевірку: якщо `p.user_id === '16778240'` або в кімнаті був лише 1 учасник при тривалості $\ge 15$ хв — ця особа визначається як `Викладач (Організатор)`.
  * Реальне ім'я вчителя витягується безпосередньо з сесії учасника-хоста замість статичної назви акаунту `Empire Group`.

### Проблема 3: Повторні підключення одного студента (Reconnects / Network Drops)
* **Контекст:** Якщо у студента переривається зв'язок, Zoom API повертає окремий запис для кожного нового входу з частковою тривалістю.
* **Рішення:**
  * Впроваджено агрегацію учасників через `Map`: ключем є `email` або `name.toLowerCase()`.
  * Тривалості сумуються, зберігається перший `join_time` та останній `leave_time`.

### Проблема 4: Одиниці вимірювання тривалості в Zoom API
* **Контекст:** Zoom у об'єкті `meeting` повертає тривалість у **хвилинах**, а у списку `participants` — у **секундах**!
* **Симптом:** Раніше через плутанину секунд і хвилин сесія у 201 секунду інтерпретувалася як 3 години 21 хвилина.
* **Рішення:** Створено роздільні утиліти конвертації: `formatMinutesDuration(minutes)` для зустрічей та `formatSecondsDuration(seconds)` для учасників.

## 6. Необхідні змінні середовища (.env)

Для роботи сервісу потрібен Server-to-Server OAuth додаток у Zoom App Marketplace з наступними правами (Scopes):
* `user:read:admin`
* `report:read:admin`
* `meeting:read:admin`

Змінні середовища:
```env
ZOOM_ACCOUNT_ID=ваш_account_id
ZOOM_CLIENT_ID=ваш_client_id
ZOOM_CLIENT_SECRET=ваш_client_secret
```

## 7. Напрямки для подальшого ресерчу та наступні етапи розвитку (Backlog)

Для подальшого обговорення в чаті Gemini рекомендуються наступні напрямки:

1. **Webhook-driven архітектура (Real-time замість Polling):**
   * Перехід з опитування Report API на вебхуки Zoom Event Subscriptions (`meeting.ended`, `meeting.participant_joined`, `meeting.participant_left`).
   * Це повністю зніме проблему Rate Limits і дозволить вести актуальну базу занять в режимі реального часу.
2. **База даних та персистентність:**
   * Зараз дані збираються «на льоту» (on-the-fly) безпосередньо з Zoom.
   * Доцільно додати легку БД (Supabase, PostgreSQL, PlanetScale, Redis) для кешування вже завершених занять, щоб не смикати Zoom за минулі періоди.
3. **Метчинг студентів з CRM/LMS:**
   * Багато студентів заходять без пошти («Гість»), вказуючи лише ім'я або нікнейм у Zoom.
   * Ресерч способів автоматичного зіставлення:
     - За розкладом уроку та групою.
     - За унікальним посиланням підключення (Registration URL / Personal Link з передачею `zak` токена або `customer_key`).
4. **Експорт та інтеграція звітності:**
   * Генерація CSV/Excel або пряма передача даних у Google Таблиці / 1С / Notion для бухгалтерського розрахунку виплат викладачам.
